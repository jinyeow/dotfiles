# Replying to PR review comments

Applies when you answer review comments on a pull request as the code's author, or on the author's behalf. Applies on ADO and GitHub alike.

- For each review comment, first explain why the code is written as it is. Then weigh the reviewer's point against the author's, present the options with their trade-offs, and let me choose. Do not implement the suggestion by default.
- Address comments one by one, with one commit per comment. Push only when I ask. For each thread, ask me for the reply text unless I give it.
- Thread replies carry only the concession, the change, and the evidence. No commit ids. Do not restate unchanged or already-standard behaviour. Put the evidence line on the one thread whose tests prove the change. Refer to other threads by wording, never by id.
- Never mark a thread resolved yourself. Resolution is the reviewer's call.
